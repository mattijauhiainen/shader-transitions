Matrix Multiplication

Matrices are tables of numbers. Multiplying two matrices produces a third matrix, computed by a very specific recipe. Once you internalize the recipe, you realize it's just a lot of dot products glued together.

The recipe

Given two matrices A and B, the product C = A × B has entries:

C[row][col] = dot product of row `row` of A with column `col` of B

In a formula, summed over k:

C[i][j] = Σ A[i][k] × B[k][j]

That's it. Every entry of the output is one dot product. A 4×4 times 4×4 produces a 4×4 matrix with 16 entries, so it's 16 dot products. Each dot product sums 4 multiplications. 64 multiplications + 48 additions in total.

Matrices are transformations

The recipe for multiplication looks arbitrary, but it isn't. To see why, you have to understand what matrices are for: a matrix is a way to encode a function — a transformation — that takes a vector and gives back another vector.

"Rotate by 30°" is a transformation. "Scale by 2" is a transformation. "Skew along the x-axis" is a transformation. Each one can be packaged into a matrix, and then applied to a vector by multiplication:

output_vector = M × input_vector

The whole multiplication recipe — including the "dot product of a row with a column" rule — is designed to make this work. It's not the recipe deciding what matrices can do; it's matrices' role as transformations dictating what the recipe must be.

Linear transformations specifically

Matrices encode a specific kind of transformation, called linear. A transformation T is linear when it satisfies two properties:

T(v + w) = T(v) + T(w)        (distributes over addition)
T(α · v) = α · T(v)           (scales with scalar multiplication)

In plain English: "transforming a sum is the same as summing the transforms" and "doubling the input doubles the output." Geometrically, linear transformations preserve the origin, keep straight lines straight, and keep parallel lines parallel. They can rotate, scale, shear, reflect, project — but they cannot translate (translation moves the origin, which breaks linearity).

This restriction sounds limiting until you realize the consequence: a linear transformation is completely determined by where it sends the basis vectors. If you know where x̂ lands and where ŷ lands, you know where every other point lands — by linearity:

v = v.x · x̂ + v.y · ŷ
T(v) = T(v.x · x̂ + v.y · ŷ) = v.x · T(x̂) + v.y · T(ŷ)

The transformed point is just a weighted sum of "where x̂ went" and "where ŷ went," with the weights being the original coordinates of v. This is the fundamental insight matrices encode.

The columns are where the basis vectors land

Given that a linear transformation is fully described by the destinations of the basis vectors, a matrix simply stores those destinations as its columns:

M = [ x̂ went to here │ ŷ went to here │ ẑ went to here ]
      ↑                ↑                ↑
      column 0         column 1         column 2

So when you see a 2D matrix:

┌ 2  -1 ┐
└ 0   3 ┘

...you can read it directly as: "x̂ ends up at (2, 0), ŷ ends up at (-1, 3)." The transformation has been completely described by those four numbers.

A few things to notice while you play with it:

  • Identity — the matrix where i = (1, 0) and j = (0, 1) does nothing. The F stays put. This is the "no transformation" matrix.
  • Rotate — both basis vectors swing together; the F rotates rigidly. The rotation matrix's columns are exactly (cos θ, sin θ) and (-sin θ, cos θ) — i.e. where x̂ and ŷ land after rotating.
  • Singular (collapse to a line) — if i and j happen to point in the same direction (i.e. they're parallel), the entire 2D plane gets squashed onto a single line. The F flattens. The matrix is singular — information has been lost and you cannot invert it.
  • Reflect — if you make i = (-1, 0), the F flips horizontally. Negative basis-vector destinations flip orientation.

Applying = computing the weighted sum

The matrix tells us where the basis vectors went. Applying it to an arbitrary vector v = (v.x, v.y) is then mechanical:

T(v) = v.x · i + v.y · j
     = v.x · (column 0) + v.y · (column 1)

Written out in components, with column 0 = (i.x, i.y) and column 1 = (j.x, j.y):

T(v).x = v.x · i.x + v.y · j.x
T(v).y = v.x · i.y + v.y · j.y

Or, in matrix form:

┌ T(v).x ┐   ┌ i.x  j.x ┐ ┌ v.x ┐
└ T(v).y ┘ = └ i.y  j.y ┘ └ v.y ┘

Each output entry is a row of M dot-producted with v. The "dot row with vector" recipe is the linear-combination formula written sideways. Not arbitrary — exactly the arithmetic that "weighted sum of basis destinations" requires.

Multiplying matrices = composing transformations

So far we've talked about applying a transformation to a vector: output = M × v. What if we want to apply two transformations in sequence? Rotate, then scale?

If A is the scale matrix and B is the rotation matrix, applying B first and then A to a vector v looks like:

step 1: u = B × v       (rotate)
step 2: w = A × u       (then scale)

combined: w = A × (B × v)

Matrix multiplication is defined so that this is the same as multiplying B and A together first into a single combined matrix:

w = (A × B) × v

That is the entire reason matrix multiplication exists, and the entire reason its recipe is "rows dot columns." The recipe is whatever it needs to be so that composing transformations into a single matrix gives a matrix that, when applied to a vector, produces the same result as applying the two original transformations in sequence.

Why the recipe is exactly "rows dot columns"

Here's the derivation in one direction. The matrix A × B represents "apply B, then A." Its columns must be the destinations of the basis vectors under that combined transformation:

column 0 of (A × B) = A × (B × x̂)
column 1 of (A × B) = A × (B × ŷ)
...

But B × x̂ is just column 0 of B. So column 0 of A × B is A applied to column 0 of B. And applying A to a vector is "weighted sum of A's columns with weights from the vector's components" — i.e., each entry of the result is a dot product of a row of A with that column of B. That's the recipe.

You don't have to memorize "rows times columns." You have to remember "columns of the product are A applied to the columns of B" — and the rows-times-columns formula falls out automatically.

This is why order matters

"Rotate then scale" and "scale then rotate" give different results when the rotation and scale aren't uniform. Try it: rotate a tall rectangle 45°, then scale x by 2 — you get a parallelogram. Scale x by 2 first, then rotate 45° — you get a different parallelogram. The matrices A × B and B × A are different matrices because the transformations they represent are different sequences.

Matrix multiplication is non-commutative because composing transformations is order-sensitive. The algebra simply reflects the geometry.

Critical properties

Associative — yes

(A × B) × C  =  A × (B × C)

You can group multiplications however you like. This is why mvp = projection × view × model can be computed as (projection × view) × model or projection × (view × model) — both produce the same result, but the first one lets you compute projection × view once and reuse it for every model.

NOT commutative

A × B  ≠  B × A  (in general)

Order matters. This is the single most important fact about matrix multiplication. Translating then rotating gives a completely different result from rotating then translating — and the matrices reflect that.

Try it: rotate a vector 90° then translate it by (5, 0), versus translate then rotate. You end up in different places.

Identity exists

I × A = A × I = A

There's a special matrix I (the identity matrix — 1s on the diagonal, 0s elsewhere) that acts like the number 1: multiplying by it leaves the other matrix unchanged. It represents the "do nothing" transformation.

The right-to-left reading order

When you see M × v, the matrix is on the left. When you compose transformations, you read the multiplication chain right to left:

final = projection × view × model × vec4(localPos, 1.0)

The point starts in local object space (the rightmost thing). It first gets multiplied by model, moving into world space. Then view, moving into camera space. Then projection, into clip space. The matrix nearest to the vector acts first.

This is just a convention — but it's the convention used by every graphics API (GLSL, HLSL, math libraries), so you might as well internalize it.

How your multiply implements the recipe

Here's your mat4.ts multiply, annotated:

export function multiply(out: Mat4, a: Mat4, b: Mat4): Mat4 {
  const res = new Array<number>(16);
  for (let row = 0; row < 4; row++) {           // for each output row
    for (let col = 0; col < 4; col++) {         // for each output column
      let sum = 0;
      for (let k = 0; k < 4; k++) {              // dot product of row of a with col of b
        sum += a[k * 4 + row] * b[col * 4 + k];
      }
      res[col * 4 + row] = sum;                  // write into result
    }
  }
  for (let i = 0; i < 16; i++) out[i] = res[i];  // copy temp to out (aliasing safety)
  return out;
}

The inner loop is the dot product. The two outer loops walk every (row, col) cell of the output. The strange-looking indexing k * 4 + row versus col * 4 + k is column-major arithmetic: to walk down a column you step by 1, to walk across a row you step by 4.

One last picture

A useful mental model: think of a matrix as a stack of column vectors. A × v is then "a weighted sum of A's columns, where the weights come from v":

A × (v.x, v.y, v.z, v.w)  =  v.x · col0  +  v.y · col1  +  v.z · col2  +  v.w · col3

This is the same recipe written differently. It's especially useful for understanding what a matrix does: A's columns are where the basis vectors go after the transformation. The first column is "where the x-axis lands"; the second column is "where the y-axis lands"; and so on.

So when you build a rotation matrix and the second column is (0, cos(θ), sin(θ), 0), that's literally telling you: "after this transformation, the y-axis ends up at that location." Designing matrices becomes much easier once you think of columns as destinations of basis vectors.
