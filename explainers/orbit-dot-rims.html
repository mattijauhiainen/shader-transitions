Orbit dot rims

The orbit transition flies a camera around the dot grid and shows it from many angles, then drops the camera back into the same flat pose every other transition uses. Two problems show up at the dot's edges: one at handoff (the moment orbit ends and the next transition takes over), and one mid-flight (the dots get noisy halos when the camera is at an angle). This is what the problems are and how we fixed them.

The setup

A dot is a circle of radius r pixels, where r comes from the cell's luminance. The resting halftone (and every 2D transition like wipe) draws it with a 1-pixel-wide anti-aliased rim:

alpha = smoothstep(r + 0.5, r - 0.5, dist_from_center_in_pixels)

Inside the dot, alpha = 1. Outside, alpha = 0. Right at the edge, alpha = 0.5. The 1-pixel feather is what makes circles not look like staircases on a square pixel grid.

Orbit can't draw the dot the same way, because it's in 3D — the camera moves, dots tilt and foreshorten. Orbit instead draws each dot as a tiny billboard (a quad always facing the camera), and the fragment shader inside that quad recovers the dot's apparent screen radius and runs the same smoothstep.

Problem 1: the dot edges didn't match at handoff

At the very last frame of orbit, the camera is dead-on in front of the dot plane — the same view as the resting halftone. The next transition takes over from there. So orbit's last frame and the next transition's first frame should be pixel-identical. They weren't: some dots looked subtly different, especially small ones from dark cells.

The cause was how the anti-aliasing was computed. The old orbit shader used fwidth() in normalized coordinates inside the billboard (the impostor's [-1, 1] space) instead of in pixels:

float r = length(vCorner);              // 0 at center, 1 at dot edge
float aa = fwidth(r);                    // how fast r changes per pixel
float alpha = 1 - smoothstep(1 - aa/2, 1 + aa/2, r);

For a dot whose screen radius is 5 pixels, fwidth(r) is about 1/5 = 0.2 — so the smoothstep spans about 1 pixel of screen space. Fine. But for a dot whose screen radius is half a pixel (a dark, low-luma cell), fwidth(r) is about 2, and the smoothstep spans the whole dot. The dot turns into a fuzzy blob instead of a tight dot.

The fix

Do anti-aliasing in actual pixels, not in impostor coordinates. The vertex shader projects the dot's center, reads gl_Position.w (which is its depth from the camera), and converts the dot's world radius into a screen pixel radius — call it vRadiusPx. The fragment shader uses the same smoothstep the resting halftone does:

float distPx = length(vCorner) * vRadiusPx;
float alpha = smoothstep(vRadiusPx + 0.5, vRadiusPx - 0.5, distPx);

Now the feather is always 1 pixel wide, regardless of dot size. Big dots match. Small dots match. Handoff is pixel-identical.

Subtle detail: the billboard needs to be slightly bigger than the dot itself, otherwise the AA tail (the part where alpha drops from 0.5 to 0) is cut off at the billboard's edge. We scale the billboard up by half a pixel of headroom. For sub-pixel dots we cap the scale-up at ~12% so the billboard doesn't balloon to absurd sizes — those dots are below one pixel anyway, the cap is invisible.

Problem 2: noisy halos around the dots mid-flight

With the handoff fixed, a second problem became visible while the camera was actually moving. The dots had flickering, dark halos around their edges. The halos shifted every frame.

Why that happens

3D rendering uses a depth buffer: for every pixel on the screen, the GPU remembers how far away the closest thing drawn there is. When a new fragment comes in, the GPU compares its depth against what's in the buffer; if the new fragment is farther, it's thrown away (it'd be behind something already drawn). This is how a closer object correctly hides a farther one.

Mid-flight, dots that are physically far apart in the world get projected close together on screen due to perspective. Two dots can land on overlapping screen pixels — one closer to the camera, one farther. The depth test sorts them out correctly… for the dot centers. But the dot has an AA rim where alpha is partial (0.05, 0.3, 0.5…), and those rim fragments also write into the depth buffer. So:

  1. The near dot's solid center writes its depth. ✓
  2. The near dot's rim writes the same depth, even at pixels where alpha is just 0.05.
  3. The far dot tries to draw at one of those rim pixels. Its depth fails the test (it's behind). It's thrown away entirely.
  4. The screen pixel ends up showing 0.05 × nearColor + 0.95 × black instead of 0.05 × nearColor + 0.95 × farColor — a dark patch.

And because the camera moves every frame, which dot's rim covers which other dot's center shifts constantly — the halos shimmer. That's the "noise" at the edges of the balls.

The fix: split the draw into two passes

We want the depth test to do its job for the solid centers (so closer dots properly hide farther ones), but we don't want the AA rims to write into the depth buffer (so they can't block anything). So we render orbit's dot grid twice:

Pass Color writes Depth writes What renders
1: depth lay-down off on discard if alpha < 0.95 — only the solid interior of each dot writes depth
2: color on off discard if alpha ≈ 0 — the full dot, rim included, composited with blending

The fragment shader is the same in both passes; only a uMinAlpha uniform changes between them. After pass 1, the depth buffer remembers each dot's center but nothing about its rim. Pass 2 then:

  • Draws a near dot's center → passes depth test → renders.
  • Draws a near dot's rim where there's nothing behind → no depth at that pixel → renders.
  • Draws a near dot's rim where a far dot's center sits behind it → near's depth is closer → passes → composites over the far center. No dark halo.
  • Draws a far dot's center where a near dot's center sits in front → fails depth → discarded. Correct occlusion.
One gotcha: pass 2's own solid-center fragments are at the same depth as what pass 1 wrote — so the default LESS depth test would reject them (a fragment at depth z isn't less than a buffer at depth z). We switch to LEQUAL for the orbit draw so equal depths survive. The first version of the fix without this switch made every dot's interior render as solid black — pass 1 wrote depth, pass 2's interior failed the test, and only the rim came through.

Summary

Two unrelated-looking problems, both at the dots' edges, both with focused fixes:

  1. Handoff didn't match the resting halftone. The anti-aliasing was computed in the billboard's normalized space, so it scaled with the dot — fine for big dots, awful for small ones. Fix: pass the dot's screen pixel radius through to the fragment shader and use the same pixel-space smoothstep every 2D transition uses.
  2. Mid-flight rims left dark halos. AA-rim fragments wrote into the depth buffer, blocking dots that should have shown through behind them. Fix: two-pass draw — first pass writes only the solid centers' depth, second pass writes only color and tests against that depth field. Use LEQUAL so pass 2's own centers survive pass 1's writes.
