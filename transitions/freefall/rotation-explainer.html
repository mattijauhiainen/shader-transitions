Euler-Angle Rotation Matrices

A textbook walkthrough of the math behind a yaw-pitch-roll camera, ending in the exact 9 entries used in the freefall transition.

1. What a rotation matrix actually is

A rotation matrix is a 3×3 grid of numbers that, when multiplied with a 3D vector, returns that same vector after being rigidly rotated around the origin. Lengths and angles are preserved — nothing stretches, nothing skews.

The three columns of any rotation matrix have a beautiful geometric meaning: column i is where the original axis i ends up after the rotation. Column 0 = where the X axis goes, column 1 = where Y goes, column 2 = where Z goes. That's why the columns are always unit length and mutually perpendicular: the rotated axes still form an orthonormal frame.

2. Deriving the 2D rotation matrix

Before tackling 3D, let's earn the 2D version from scratch. Take a point p = (x, y) and rotate it counterclockwise by angle θ around the origin. We want the new coordinates (x', y'), and we want them as a matrix.

The trick is to look at where the basis vectors land. By the very definition of cosine and sine:

  • The X-axis unit vector (1, 0), rotated by θ, lands at (cos θ, sin θ) — that's literally the point on the unit circle at angle θ.
  • The Y-axis unit vector (0, 1) is just X rotated 90° further along, so it lands at angle θ + 90°, which is (−sin θ, cos θ).

Any point (x, y) is just x · X̂ + y · Ŷ. After the rotation it becomes x · (rotated X̂) + y · (rotated Ŷ):

x' = x · cos θ + y · (−sin θ)
y' = x · sin θ + y · cos θ

That [[cos, −sin], [sin, cos]] block is the only place those four entries come from. Everything else in this document is consequences. Notice the columns of the matrix are exactly the rotated basis vectors — the same principle from Section 1.

Quick sanity check. Plug in θ = 90°: cos = 0, sin = 1. The matrix becomes [[0, −1], [1, 0]]. Apply it to (1, 0): get (0, 1). ✓ X axis became Y axis. Apply to (0, 1): get (−1, 0). ✓ Y axis became −X. That's a counterclockwise quarter turn.

If you flip the convention — clockwise positive, or use a left-handed coordinate system — the off-diagonal signs swap. That single choice is the entire source of sign confusion in graphics code.

3. Lifting to 3D: rotate around an axis

A 3D rotation around an axis just runs the 2D rotation in the plane perpendicular to that axis, while leaving the axis itself untouched. Concretely, for rotation around Z, the (x, y) plane spins by θ and z stays put. Stack a "do nothing to z" row and column onto the 2D matrix:

The reason is a bookkeeping issue, not a geometric one. We always want positive θ to mean "counterclockwise when looking from positive axis back toward origin," and we want the 2D rotation block to keep the same sign pattern. That works if we list each rotation's plane in the cyclic order (x, y, z) → (y, z) → (z, x):

If we wrote Ry in (z, x) order, the 2D block would look identical to the others:

cos β−sin β
sin βcos β

But our matrix has to be written in (x, y, z) order so it composes with the others. When we reshuffle rows and columns from (z, x) back to (x, z), the off-diagonal entries swap places — and that's exactly why the negative sign migrates from the top-right to the bottom-left.

So the "weird" sign pattern in Ry is the cost of writing all three matrices in (x, y, z) order while their underlying 2D rotations live in different planes.

Each one fixes its own axis (the row/column of 1s and 0s) and does a 2D rotation in the plane perpendicular to it.

5. Composition: order matters

To reach a general orientation we apply several elementary rotations in sequence. In matrix notation, applying R1 first and R2 second to a vector v is written

v' = R2 · R1 · v

The matrix on the right hits the vector first. So in

R = Rz(γ) · Rx(α) · Ry(β)

yaw is applied first, then pitch, then roll. Matrix multiplication is not commutative: pitching then yawing produces a different orientation than yawing then pitching. Try it with your hand: nose-down then turn-left is not the same as turn-left then nose-down.

7. Column-major storage

A 3×3 matrix has 9 entries; a flat Float32Array has 9 slots. There are two conventions for laying them out:

index012345678
row-majorR00R01R02R10R11R12R20R21R22
column-majorR00R10R20R01R11R21R02R12R22

OpenGL and WebGL use column-major. So when the code sets rot[5] = sa, that's index 5 = row 2, column 1 in column-major terms = the (Z, Y) entry of R, which from our table above is sα. ✓

8. Reading the 9 lines of code

Lining up the assignments with the column-major layout:

rot[0] = cg*cb − sg*sa*sb;     // R₀₀  (X column, X row)
rot[1] = sg*cb + cg*sa*sb;     // R₁₀
rot[2] = −ca*sb;               // R₂₀
rot[3] = −sg*ca;               // R₀₁  (Y column, X row)
rot[4] = cg*ca;                // R₁₁
rot[5] = sa;                   // R₂₁
rot[6] = cg*sb + sg*sa*cb;     // R₀₂  (Z column, X row)
rot[7] = sg*sb − cg*sa*cb;     // R₁₂
rot[8] = ca*cb;                // R₂₂

Every line matches the corresponding entry of the symbolic R we worked out in Section 6. The middle column (rot[3..5]) is noticeably simpler because the middle column of Ry(β) is (0, 1, 0)T, which kills the β terms during the multiplication.

9. Geometric reading

Recalling Section 1: the columns of R are the images of the world axes after the full yaw-pitch-roll rotation, expressed in the camera's frame.

  • Column 0 (rot[0..2]) — where world X ends up.
  • Column 1 (rot[3..5]) — where world Y ends up. Its third component is sin α: pitching the camera tilts the world's vertical axis by exactly that much, regardless of yaw or roll.
  • Column 2 (rot[6..8]) — where world Z ends up.

So the cryptic-looking 9 lines are nothing more than: "given yaw, pitch, and roll, here is where each world axis points from the camera's perspective — written down column by column the way the GPU expects."

10. Using R in the vertex shader

So far R lives in JavaScript. To actually see a rotated world, every vertex of every particle has to be transformed by R on the GPU. The freefall shader does this in three conceptual stages: world → camera → screen. Here's the relevant slice of freefall.vert.glsl:

uniform vec3 uCamPos;
uniform mat3 uCamRot;       // ← our R, uploaded via uniformMatrix3fv
uniform float uFOCAL_LEN;
uniform vec2  uVIEWPORT;

void main() {
    // ... build worldPos for this particle ...
    vec3 worldPos  = vec3(worldXY, particleZ);

    // Stage 1: world → camera
    vec3 camSpace  = uCamRot * (worldPos - uCamPos);

    // Stage 2: camera → screen (pinhole projection)
    float perspScale = uFOCAL_LEN / camSpace.z;
    vec2  projected  = camSpace.xy * perspScale + uVIEWPORT * 0.5;

    // Stage 3: screen pixels → clip space
    float ndcZ = (camSpace.z - uNEAR_CLIP) / (uFar - uNEAR_CLIP) * 2.0 - 1.0;
    gl_Position  = vec4(projected / uVIEWPORT * 2.0 - 1.0, ndcZ, 1.0);
}

Stage 1: world → camera

This is the line that consumes our hard-won R:

vec3 camSpace = uCamRot * (worldPos - uCamPos);

Two things happen here, in order: a translation and then a rotation.

  1. worldPos − uCamPos shifts the origin to the camera. After this subtraction, a vector that points from the camera to the particle replaces the absolute world position. The camera is now sitting at (0, 0, 0).
  2. uCamRot * (...) applies our rotation R. Because R was built as the world-to-camera rotation, the result expresses that "camera-to-particle" vector in the camera's own coordinate frame: +X is camera-right, +Y is camera-up, +Z is the direction the camera is looking.

The translation has to come before the rotation. R is a pure rotation around the origin — it can't move the camera to the origin, only spin things around it. So we move first, spin second.

A subtlety: the code uses the same R we built as world→camera, applied directly. If R were instead the camera-to-world rotation (the way you'd describe "the camera is yawed 30° to the left"), the shader would need its inverse. Since rotation matrices are orthogonal, the inverse is just the transpose — but it's much cleaner to build R in the right direction up front, which is exactly what Section 4's Rz·Rx·Ry derivation does.

Stage 2: camera → screen (pinhole projection)

Once a point is in camera space, projecting it to a 2D image is a similar-triangles argument. Imagine a virtual image plane sitting at distance f (the focal length) in front of the camera, perpendicular to the camera's +Z axis. A particle at camera-space position (X, Y, Z) appears on that plane at:

x_screen = f · X / Z      y_screen = f · Y / Z

The shader rewrites this as perspScale = uFOCAL_LEN / camSpace.z and then camSpace.xy * perspScale, plus an offset by half the viewport so the image's origin sits at the center of the screen, not the corner:

vec2 projected = camSpace.xy * perspScale + uVIEWPORT * 0.5;

perspScale is the entire perspective effect in one scalar. The 1/Z shrinks distant things and enlarges close ones — exactly what the eye does. (It's also why the shader bails out earlier when camSpace.z < uNEAR_CLIP: dividing by very small or negative Z produces nonsense.)

This is a hand-rolled projection — no projection matrix, no gl_Position = P · V · M · vertex. The freefall code skips the conventional matrix pipeline because it's drawing screen-space billboards: each particle becomes a 2D quad sized in pixels, so it's natural to compute pixel coordinates directly. A typical 3D engine would instead bundle this divide-by-Z into a 4×4 projection matrix and let the GPU's built-in perspective divide do the work.

Stage 3: pixels → clip space

WebGL doesn't actually want pixel coordinates in gl_Position; it wants normalized device coordinates (NDC), where the visible region is the cube from −1 to +1 on every axis. Converting pixels to NDC is one line:

gl_Position = vec4(projected / uVIEWPORT * 2.0 - 1.0, ndcZ, 1.0);

Dividing by the viewport puts the screen in [0, 1]. Multiplying by 2 and subtracting 1 stretches that to [−1, +1]. The Z component is similarly remapped from the [near, far] range to [−1, +1] so the depth buffer sees a full-resolution depth value.

Setting w = 1 in gl_Position tells the GPU to skip its automatic perspective divide. We've already done it ourselves in Stage 2.

The full pipeline at a glance

And that's the payoff for all the matrix algebra of Sections 1–9: a single uCamRot * (worldPos - uCamPos) in the shader, evaluated for every vertex of every particle, every frame — turning yaw, pitch, and roll into a believable camera orbit.
